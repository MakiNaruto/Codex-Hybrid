# 桌面版实施计划（已确认产品基线）

本文汇总截至 2026-10-26 逐轮讨论中已经确定的产品边界，并提出技术拆分与验收方案。产品基线已经确认；具体技术方案在阶段 0 验证后冻结。尚未验证的能力不视为实现承诺。阶段 0 已开始，结果见[验证记录](stage0-validation.md)；尚未进入生产功能开发。

## 当前推进：通过网页版迭代验证功能

2026-10-27 调整：持续在现有网页上迭代，暂不推进 Tauri、桌面打包、托盘或原生进程控制。下文桌面方案作为后续产品基线保留，阶段 0 的双平台验证不再阻塞网页开发，也不因此标记通过。

网页验证进度：

- 试用修正：网页开启和关闭接入时，进程检测均为提示信息，确认活动影响后继续，不因运行或未知状态阻止。保留备份、预览版本及数据变化校验；CLI 离线迁移仍保留退出要求。进程检测不再使用宽泛的 `codex-*` 前缀，读取权限不足显示未知，且与任务忙碌状态分开。

- 已实现：接入切换预览、确认取消、接入前配置备份恢复、外部修改拦截。
- 本轮实现：网关活动请求计数，网页每秒读取状态；切换预览附带活动快照。只保留内存计数，不保存请求内容或活动历史；Codex 任务状态固定为未知。
- 新增：网页“运行与诊断”，显示服务运行时长、按需读取日志尾部最近 20 条错误摘要、下载白名单 JSON 诊断。最多读取日志末尾 128 KiB，不导出原始日志或配置。
- 暂缓：按用户要求，暂时不推进冲突字段展示与修复流程；已有冲突拦截继续保留。
- 已补齐：首次安装可跳过模型配置，空模型目录可进入管理页；使用准备概览、凭据可读取状态、厂商与模型筛选、模型 key 复制、连接测试耗时、厂商请求超时编辑。
- 已补齐：未保存厂商草稿标记、离开/刷新/切换来源前提醒，保存其他厂商时保留草稿；开启和关闭各自保存 Windows 桌面端操作设置；不再维护手动重启确认或待重启状态。
- 已补齐：服务连接与超时反馈，运行日志及错误日志按 2 MiB 轮转并各保留 3 份旧文件，超大元数据记录压缩为摘要；诊断导出仍按白名单生成。
- 后续：配置业务层进一步解耦，以及使用真实厂商/真实 Codex 会话的人工验收。桌面原生能力继续暂缓。试用入口与验证记录见[网页试用清单](../../docs/zh-CN/web-trial.md)。

活动观测验收：官方和第三方请求通过共同入口计数；请求与流结束或异常时释放计数；并发上限拒绝不计入活动；检测失败显示未知。未检测到网关请求不代表 Codex 空闲，预览后也可能出现新请求。网页仍由用户手动退出并重开 Codex。

现阶段优先在现有管理页复用接入预览、确认、配置备份与恢复、冲突检测和操作状态；复杂桌面端暂缓。网页版本在配置切换确认中支持可选的 Windows 桌面端启动或正常重启，每次只尝试一次；关闭接入时未运行则不启动，关闭失败仍应用配置，配置失败不再启动。CLI / VS Code 自行重启，不维护客户端加载状态。管理服务与网关保持运行，尚未实现完整桌面基线的生命周期、Codex 任务活动检测与托盘，也不表示阶段 0 已通过。后续桌面实现继续以本文完整产品基线为目标。使用说明见[网页接入开关](../../docs/zh-CN/usage.md)。

## 2. 拟定架构

```text
Tauri 桌面应用
├─ 前端：窗口、配置表单、运行状态、日志与操作反馈
├─ Rust：托盘、单实例、Python 进程监督、Codex 应用启停
└─ Python 控制进程（随应用打包，通过私有通信通道接收管理操作）
   ├─ 配置管理：厂商、模型、来源、目录生成、Codex 配置事务
   ├─ 单次连接测试：用户明确触发，不依赖网关监听
   └─ 网关运行单元：用户开启 Codex 接入后才启动监听
      ├─ 现有路由、流式适配和工具调用逻辑
      └─ 健康状态与活动请求观测
```

上图是待原型验证的技术方案：打开应用时允许启动配置管理所需的 Python 控制进程，但模型转发监听保持停止。网关启停由“Codex 接入”主开关统一协调，不向用户暴露第二个服务开关。网关采用子进程还是受控线程，在阶段 0 验证后定稿；优先考虑独立子进程，便于故障隔离。

控制层复用业务函数，不调用交互式 CLI，不维护第二份厂商配置。现有 Management 对 gateway.settings、并发槽和路由函数的依赖需要抽离。前端框架与组件库在界面骨架阶段确定，不照搬 Clash Verge Rev 的整个依赖树。

桌面操作经 Tauri 命令和私有控制通道到达 Python。不得为适配桌面页面而放宽现有管理 HTTP 接口的 Host、Origin 或认证检查。网关继续提供 Codex 所需的本地 HTTP 接口。

## 3. 状态与生命周期

界面以“Codex 接入”主开关表达用户操作，以状态文字区分未接入、正在开启、已接入、正在关闭和故障。网关及磁盘配置状态作为辅助详情展示。主开关相关的重启统一在确认后执行，不保留用户主动选择的“已保存、稍后重启”中间态；配置已写入但重启失败属于明确故障，不能显示切换成功。

| 操作或事件 | 行为 |
| --- | --- |
| 打开应用 | 读取并校验默认目录；不启动网关、不自动写 Codex 配置 |
| 无配置或无模型 | 可以进入界面、保存配置；连接测试仅由用户触发 |
| 开启 Codex 接入 | 先校验配置、实例和端口，准备变更预览；需要重启则检测活动并等待“应用并重启”确认，之后启动网关并通过健康检查、保存基线、提交配置和重启；Codex 未运行则不弹重启确认 |
| 关闭 Codex 接入 | 先准备原生配置恢复预览；需要重启则检测活动并等待“应用并重启”确认，之后恢复配置、正常重启 Codex、停止网关；取消则维持原状态 |
| 模型列表变更 | 更新目录；提示重启，绝不自动重启 Codex |
| Key 或 API 地址变更 | 延续现有下一轮请求生效的行为 |
| 退出 | 执行与关闭接入相同的恢复流程；任一步失败保持可恢复状态，不静默停止网关 |
| 网关意外退出 | 有限次数重试并退避；不将用户主动停止识别成崩溃 |
| 连续启动失败 | 停止自动重试，保留界面，展示原因及恢复接入前配置入口 |
| 外部修改冲突 | 不覆盖外部修改，暂停相关写入，展示冲突与修复入口 |

恢复接入前原生配置与重启流程（关闭接入与退出共用）：

1. 判断 Codex 是否运行、当前配置及已知生效状态是否依赖网关。
2. 检查外部修改，准备恢复预览。恢复目标是本次接入前被本工具修改的字段，包括字段原先不存在的情况；不固定写成 model_provider=openai，不整份覆盖历史配置。原有路由不在首版兼容范围时应在开启前说明并阻止接入，不能先改写再声称可恢复。
3. 如 Codex 需要重启，执行下面的双重活动检测，展示结果及预览，提供“应用并重启 / 取消”。取消时不修改配置、不停止网关；退出场景可留在托盘。确认后重新校验冲突，备份并提交配置，再执行后续步骤。
4. 正常关闭 Codex，确认目标应用进程已退出，再启动 Codex；不自动强杀。
5. 确认新应用进程成功启动，并重新校验配置；首版不宣称已验证其内部加载结果或任务恢复。
6. 正常路径完成后停止网关，按用户原操作留在界面或退出。

如 Codex 本来未运行，跳过重启确认和应用启停，提交恢复配置后直接停止网关。两方向的主开关操作均串行执行，处理中禁止重复提交。用户确认前取消保持原状态；确认后发生故障则显示实际配置与进程状态，保留网关（若可运行）及恢复入口，不把失败视为用户取消。正常关闭受阻时仅在原配置仍满足事务校验的情况下回滚本次写入；回滚遇到外部冲突则停止写入并提示修复。

取消、关闭受阻、启动失败、配置冲突均取消自动退出并保留网关及恢复入口。若 Codex 本来未运行且配置已恢复，可直接停止。连续点击开启、重试及重启应用不能将本工具生成的配置误记为接入前基线；旧数据缺少可信基线时停止自动恢复并提供修复入口。

不提供开机自启，无法保证系统关机、强制终止或断电时完成恢复。下次打开应用须识别“配置仍指向桥接但网关未运行”，提供“恢复接入”或“恢复原生配置”入口；不擅自启动网关。

## 4. 一键重启 Codex 与双重检测

重启作用于整个 Codex 应用，提示可能影响所有窗口、主任务和子任务。正常退出后启动原应用，不承诺恢复正在执行的任务。

检测两个信号：

- 网关：统计尚未结束的请求与流，包括官方和第三方路由；异常、断开和取消均应释放活动记录。仅在内存中保存必要状态，不形成请求历史功能。
- Codex：验证能否以只读方式观察桌面应用实际使用的实例及任务运行状态。官方 App Server 文档存在运行状态和状态通知，但能否覆盖现有桌面实例仍未验证。不得通过启动另一个 App Server 推断桌面任务空闲，不为检测而恢复或执行历史对话。

对外显示“检测到忙碌”“未检测到活动”“状态未知”，附带信号来源与新鲜度。没有网关请求不代表任务结束；工具执行和等待审批也可能处于活动状态。

- 检测到忙碌：默认取消；用户可以明确选择仍然重启，但仍只正常关闭应用。
- Codex 状态不可读取：显示未知与网关检测结果，由用户确认后可继续。
- 检测到重启执行之间存在竞态，双重检测不能承诺绝对安全。首版不提供自动等待空闲后重启的后台任务。

参考：[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)。实际连接能力、权限、版本兼容与全窗口覆盖均需在阶段 0 实测。

## 5. 配置、数据与诊断

- 桌面版固定默认目录，不继承用于 CLI 自测的数据目录覆盖参数。保留现有业务文件格式，新增桌面偏好或运行时元数据采用独立文件；旧 CLI 应能继续读取业务配置。
- 不提供 CLI 安装接管或数据迁移向导；默认目录有兼容数据时校验后读取，有不兼容或损坏数据时显示修复信息，不覆盖初始化。
- 目录锁必须覆盖检查、启动和写入，不能只检查 PID 文件。CLI 若要与桌面并存自测，也需遵守同一互斥约定。
- 外部修改由写入前比较、写入时复核和语义校验保护。冲突检测具体粒度在阶段 0 定稿，至少保护本工具管理的字段，并保留无关变更。
- 冲突界面展示相关字段和修复预览，敏感值脱敏；支持重新读取，以及用户确认后重新应用接入配置。恢复原生配置时同样不能覆盖有冲突的外部变更。
- 网关未启动时允许保存配置和单次连接测试。所有付费测试请求均由用户明确点击，不在向导或启动时自动发送。
- CC Switch 仅读取配置，不回写数据库；来源切换继续保留两种来源各自已有数据。
- 日志轮转并限制体积；诊断包按字段白名单生成，剔除 Key、认证头、令牌、聊天正文和工具参数。配置及原始日志不能整份打包后仅依赖字符串替换。
- 诊断包只在本地导出，由用户自行分享，不自动上传。

## 6. 分阶段实施与验收

### 阶段 0：验证技术风险，冻结接口

交付：两平台最小 Tauri 窗口与打包 Python 原型、进程通信约定、状态定义、风险验证记录。

验收：

- Windows x64、macOS arm64 在无系统 Python 的测试环境能运行打包程序并读取静态资源。
- 关闭模型监听时仍能读取、编辑配置并执行用户触发的连接测试。
- 验证打包后资源路径、进程身份、目录权限、Unicode/空格路径和健康检查。
- 验证两平台 Codex 安装识别、正常退出与再次启动；记录关闭受阻、启动失败表现。
- 验证 Codex 状态读取的可行性及覆盖范围；不可用时确认未知状态降级方案。
- 确认目录互斥和配置冲突保护策略，以及前端与 Python 控制协议。

此阶段不过关不进入大规模界面开发。用户已确认具备 Windows x64、macOS Apple Silicon 两种设备，可配合实测；实际接入测试设备的方式、工具链和测试步骤在阶段开始时安排。Windows 本机通过不等于双平台通过。

### 阶段 1：抽离配置管理，建立运行控制

交付：独立于网关的配置业务层、打包入口、控制协议、网关监督与互斥、活动请求状态。

验收：未配置模型可启动管理界面；仅用户开启接入才启动网关；重复实例、端口冲突、崩溃重试、控制进程异常均有明确结果；既有 CLI 自测路径和业务数据保持兼容。

### 阶段 2：完成路由、重启与恢复闭环

交付：统一接入主开关、接入前配置基线、配置事务、重启检测、正常重启、关闭接入和退出流程。

验收：覆盖启动失败、确认前取消保持原状态、检测忙碌、状态未知、Codex 未运行时直接切换且不启动应用、Codex 退出受阻、再次启动失败、外部配置冲突和异常关机残留；任何失败不得静默覆盖外部配置或错误显示已完成。

### 阶段 3：实现完整桌面界面

交付：首次向导、概览、厂商与模型、来源切换、日志、设置，以及托盘。

托盘包含：打开窗口、状态、开启/关闭 Codex 接入、重启 Codex、退出。托盘与概览使用同一套接入流程，不提供独立的网关启停操作。配置无效等前置条件不满足时，明确说明并引导修复。

验收：无需终端即可完成首次配置、连接测试、模型目录发布、开启/关闭接入、正常重启及故障恢复。界面以一个主开关操作，通过统一确认完成主开关所需的重启，明确展示处理中和故障，不将仅网关运行显示为接入完成。模型目录变更仍可单独提示重启，不因此自动重启 Codex。

### 阶段 4：双平台日用测试与安装包

交付：Windows x64、macOS arm64 测试包、脱敏诊断导出、安装与手动升级说明、兼容性记录。

验收：两平台验证首次安装、旧数据启动、覆盖升级保留数据、多窗口 Codex 重启、并发流式请求、工具调用、原生子任务、网络异常、连续运行和日志轮转。验证不依赖开发机上的 Python、Git 或仓库路径。

签名准备单列为公开发布前的里程碑：确认账号、证书、macOS 签名与公证流程、Windows 签名方案及构建凭据管理。测试包验收不代表已具备公开发布条件。

## 7. 验证策略与范围限制

复用现有协议测试；新增验证集中在配置事务、状态转换、实例互斥、控制协议和进程故障恢复，不为纯样式变更添加镜像式测试。安装、签名提示和 Codex 重启需要真实双平台验证。

首版不包含：Linux、Intel Mac、Windows ARM64、开机自启、自动更新、目录切换、CLI 图形化封装、请求历史、用量统计、自动强杀 Codex、保证任务恢复。

Clash Verge Rev 作为 Tauri 桌面工程参考；不以直接 fork 整个代理项目为实施路线。引用代码须按其许可证处理。

## 9. 推进顺序与完成标准

后续恢复桌面开发时，按阶段 0 → 1 → 2 → 3 → 4 推进；当前网页工作按本文开头的网页验证进度迭代。先证明双平台打包、配置管理独立运行及 Codex 重启路径可行，再建立业务控制和恢复闭环，之后完成界面与双平台安装验收。

首版完成标准：普通用户在两种目标平台无需终端、Python 或 Git，能安装应用、配置并测试模型、通过单一主开关接入 Codex、正常重启 Codex、关闭接入恢复原生配置，并在故障时查看日志与导出脱敏诊断包。取消、冲突和失败均有明确状态与恢复入口。

当前已完成 Windows Python sidecar 隔离验证及最小 Tauri 骨架，尚未完成 Tauri 原生编译、macOS 实机和真实 Codex 重启验证，阶段 0 不标记完成。详细证据、已发现差距和复现步骤见[验证记录](stage0-validation.md)。日历工期在阶段 0 完整验证后评估；双平台测试包交付与签名后的公开发布分别验收。
