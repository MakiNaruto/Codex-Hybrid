接入开关沿用 demo：每次切换都先预览和确认；桌面操作可选，开启和关闭分别记住“每次询问 / 自动操作 / 不操作”。询问默认不勾选。开启可启动未运行的 Codex，关闭不启动未运行的 Codex。退出 Codex 失败仍尝试应用配置，提示手动重启；配置切换失败不再启动 Codex。每次桌面操作只尝试一次，不强杀、不维护待重启或手动确认加载状态。配置状态与桌面操作结果分别反馈，不宣称客户端已加载配置。该规则于本次对齐由用户确认用于后续桌面版。

当前关闭网页不会停止管理服务。管理与转发监听已拆分：未接入时可只运行管理服务；关闭接入后仅在无活动请求且未检测到相关 Codex 进程时停止转发，否则保留。桌面应用的关闭窗口、退出及安全停服仍按下文独有生命周期推进；网页已提供服务重启后的恢复选择；不能把网页切换成功当作安全停服证据。冲突字段展示及可视化修复流程不再纳入计划，已有写入拦截保留。

## 2. 拟定架构

```text
Tauri 桌面应用
├─ 前端：窗口、配置表单、运行状态、日志与操作反馈
├─ Rust：托盘、单实例、Python 进程监督、Codex 应用启停
└─ Python 控制进程（随应用打包，通过私有通信通道接收管理操作）
   ├─ 配置管理：厂商、模型、来源、目录生成、Codex 配置事务
   ├─ 单次连接测试：用户明确触发，不依赖网关监听
   └─ 网关运行单元：用户开启 Codex 接入后才启动监听
      ├─ 现有路由、流式适配和工具调用逻辑
      └─ 健康状态与活动请求观测
```

上图是待原型验证的技术方案：打开应用时允许启动配置管理所需的 Python 控制进程，但模型转发监听保持停止。网关启停由“Codex 接入”主开关统一协调，不向用户暴露第二个服务开关。网关采用子进程还是受控线程，在阶段 0 验证后定稿；优先考虑独立子进程，便于故障隔离。

控制层复用业务函数，不调用交互式 CLI，不维护第二份厂商配置。网页已新增不依赖转发监听的 ManagementContext，独立承载配置快照、连接测试及请求资源；路由与协议函数仍复用现有业务实现。前端框架与组件库在界面骨架阶段确定，不照搬 Clash Verge Rev 的整个依赖树。

桌面操作经 Tauri 命令和私有控制通道到达 Python。不得为适配桌面页面而放宽现有管理 HTTP 接口的 Host、Origin 或认证检查。网关继续提供 Codex 所需的本地 HTTP 接口。

## 3. 状态与生命周期

界面以“Codex 接入”主开关表达用户操作，以状态文字区分未接入、正在开启、已接入、正在关闭和故障。网关及磁盘配置状态作为辅助详情展示。每次切换统一在确认后执行，可不操作 Codex。配置切换完成与桌面操作结果分别显示；重启失败不能伪装为重启成功，也不将已完成的配置切换显示为未写入。不维护待重启状态或客户端加载确认。

| 操作或事件 | 行为 |
| --- | --- |
| 打开应用 | 读取并校验默认目录；不启动网关、不自动写 Codex 配置 |
| 无配置或无模型 | 可以进入界面、保存配置；连接测试仅由用户触发 |
| 开启 Codex 接入 | 先校验配置、实例和端口，准备配置及索引预览并确认；保证网关健康，按选项正常关闭 Codex，复核后提交事务，成功后按选项启动一次 |
| 关闭 Codex 接入 | 先准备字段恢复及索引预览并确认，按选项尝试正常重启已运行的 Codex；未运行不启动；配置恢复结果与桌面操作结果分别反馈；网关停止需通过桌面生命周期验收 |
| 模型列表变更 | 更新目录；提示重启，绝不自动重启 Codex |
| Key 或 API 地址变更 | 延续现有下一轮请求生效的行为 |
| 退出 | 复用关闭接入的配置恢复事务；另行判断安全停服，失败保持可恢复状态，不静默停止网关 |
| 网关意外退出 | 有限次数重试并退避；不将用户主动停止识别成崩溃 |
| 连续启动失败 | 停止自动重试，保留界面，展示原因及恢复接入前配置入口 |
| 外部修改冲突 | 不覆盖外部修改，暂停相关写入，提示用户检查配置后重新读取 |

接入切换的业务流程（开启与关闭共用，按 demo 对齐）：

1. 读取配置、可信基线及索引，生成带版本校验的预览，展示客户端进程与网关活动。进程运行或状态未知仅提示，由用户确认继续；CLI 离线迁移仍要求退出 Codex。
2. 每次都确认，可选择是否操作桌面应用。仅处理识别到的本机默认 Codex 数据目录对应桌面应用；CLI / VS Code 自行重启。取消不写配置、不补齐索引。
3. 如选择操作且 Codex 已运行，先正常请求退出；失败不强杀、不重试，继续尝试配置切换并提示手动重启。成功退出可能刷新索引，因此重新规划索引；不得接受这期间发生的外部配置变化。
4. 恢复目标仅为本次接入前被修改的路由字段，包括原先不存在的字段，保留无关修改及根级 `model`。不固定写入 `model_provider=openai`。当前仅支持原生 OpenAI 与本工具路由，profile 或其他 provider 在预检时拦截。
5. 必要时由独立 Codex 辅助进程补齐索引，复核数据后备份，提交配置、恢复元数据及索引事务。补齐与迁移边界见对齐记录；普通写入失败回滚，中断保留恢复入口。缺少可信基线不自动恢复；重复开启不能覆盖基线。
6. 配置成功后，按选项尝试启动一次。开启时允许启动原先未运行的应用；关闭时不启动原先未运行的应用。退出失败、状态未知或状态变化时提示手动处理；配置失败不再启动，即使本次已经关闭 Codex。窗口或进程出现不代表加载验证，不承诺任务恢复。

两方向串行执行，处理中禁止重复提交。配置成功、索引警告、桌面操作结果分别展示。预览失效、备份失败、实际写入失败不能降级为成功。

网页已实现基于零活动请求与进程未检测到的保守停监听判断；桌面独有的停服与退出收尾尚未实现：关闭接入可先完成配置恢复，但不能据此推断仍运行的 Codex 已停止依赖网关。正常退出失败或用户选择不操作 Codex 时，仍应保留网关和恢复入口，直到满足安全停服条件；退出应用须能取消并留在托盘。具体如何确认依赖解除与提示停服，须在桌面阶段验证并冻结，不能复用网页响应作为停服信号。

不提供开机自启，无法保证系统关机、强制终止或断电时完成恢复。下次打开应用须识别“配置仍指向桥接但网关未运行”，提供“恢复接入”或“恢复原生配置”入口；不擅自启动网关。

## 4. Codex 运行检测与重启提示

2026-10-28 范围调整：用户确认只需检测 Codex 桌面端是否运行，放弃任务状态探测，不再将其作为功能或验收目标。

重启作用于整个 Codex 应用，提示可能影响所有窗口、主任务和子任务。正常退出后启动原应用，不承诺恢复正在执行的任务。

- Codex 进程：只读检测桌面端是否运行，并区分 CLI、VS Code 等客户端；检测权限不足或身份无法确认时显示未知。进程数量不等于窗口数量，不推断任务忙碌或空闲。
- 网关活动：统计尚未结束的官方和第三方请求及流，异常、断开和取消均释放计数。仅在内存保存，不形成请求历史；零请求不代表任务结束。
- 检测到进程或活动请求时展示影响提示，由用户确认是否继续；桌面操作仍可选，且只正常关闭应用。检测未知同样提示后允许确认继续。
- 检测与执行之间存在竞态；不承诺重启绝对安全，不提供自动等待任务空闲后重启。不会连接 App Server、IPC 或读取历史来推断任务状态。

## 5. 配置、数据与诊断

- 桌面版固定默认目录，不继承用于 CLI 自测的数据目录覆盖参数。保留现有业务文件格式，新增桌面偏好或运行时元数据采用独立文件；旧 CLI 应能继续读取业务配置。
- 不提供 CLI 安装接管或数据迁移向导；默认目录有兼容数据时校验后读取，有不兼容或损坏数据时显示修复信息，不覆盖初始化。
- 目录锁必须覆盖检查、启动和写入，不能只检查 PID 文件。CLI 若要与桌面并存自测，也需遵守同一互斥约定。
- 外部修改由写入前比较、写入时复核和语义校验保护。冲突检测具体粒度在阶段 0 定稿，至少保护本工具管理的字段，并保留无关变更。
- 配置冲突时停止写入，提示用户自行检查配置后重新读取；不提供冲突字段展示、修复预览或一键重新应用流程。恢复原生配置时同样不能覆盖有冲突的外部变更。
- 网关未启动时允许保存配置和单次连接测试。所有付费测试请求均由用户明确点击，不在向导或启动时自动发送。
- CC Switch 仅读取配置，不回写数据库；来源切换继续保留两种来源各自已有数据。
- 日志轮转并限制体积；诊断包按字段白名单生成，剔除 Key、认证头、令牌、聊天正文和工具参数。配置及原始日志不能整份打包后仅依赖字符串替换。
- 诊断包只在本地导出，由用户自行分享，不自动上传。

## 6. 分阶段实施与验收

### 阶段 0：验证技术风险，冻结接口

交付：两平台最小 Tauri 窗口与打包 Python 原型、进程通信约定、状态定义、风险验证记录。

验收：

- Windows x64、macOS arm64 在无系统 Python 的测试环境能运行打包程序并读取静态资源。
- 关闭模型监听时仍能读取、编辑配置并执行用户触发的连接测试。
- 验证打包后资源路径、进程身份、目录权限、Unicode/空格路径和健康检查。
- 验证两平台 Codex 安装识别、正常退出与再次启动；记录关闭受阻、启动失败表现。
- 验证 Codex 桌面运行检测、客户端进程区分和权限不足时的未知状态提示；不验收任务状态读取。
- 确认目录互斥和配置冲突保护策略，以及前端与 Python 控制协议。

此阶段不过关不进入大规模界面开发。用户已确认具备 Windows x64、macOS Apple Silicon 两种设备，可配合实测；实际接入测试设备的方式、工具链和测试步骤在阶段开始时安排。Windows 本机通过不等于双平台通过。

### 阶段 1：抽离配置管理，建立运行控制

交付：独立于网关的配置业务层、打包入口、控制协议、网关监督与互斥、活动请求状态。

验收：未配置模型可启动管理界面；仅用户开启接入才启动网关；重复实例、端口冲突、崩溃重试、控制进程异常均有明确结果；既有 CLI 自测路径和业务数据保持兼容。

### 阶段 2：完成路由、重启与恢复闭环

交付：统一接入主开关、接入前配置基线、配置事务、重启检测、正常重启、关闭接入和退出流程。

验收：覆盖启动失败、确认前取消保持原状态、检测忙碌、状态未知、Codex 未运行时开启可选启动、关闭不启动、Codex 退出受阻、再次启动失败、外部配置冲突和异常关机残留；任何失败不得静默覆盖外部配置或错误显示已完成。

### 阶段 3：实现完整桌面界面

交付：首次向导、概览、厂商与模型、来源切换、日志、设置，以及托盘。

托盘包含：打开窗口、状态、开启/关闭 Codex 接入、重启 Codex、退出。托盘与概览使用同一套接入流程，不提供独立的网关启停操作。配置无效等前置条件不满足时，明确说明并引导修复。

验收：无需终端即可完成首次配置、连接测试、模型目录发布、开启/关闭接入、正常重启及故障恢复。界面以一个主开关操作，通过统一确认选择是否操作 Codex，并分别展示配置及桌面操作结果，明确展示处理中和故障，不将仅网关运行显示为接入完成。模型目录变更仍可单独提示重启，不因此自动重启 Codex。

### 阶段 4：双平台日用测试与安装包

交付：Windows x64、macOS arm64 测试包、脱敏诊断导出、安装与手动升级说明、兼容性记录。

验收：两平台验证首次安装、旧数据启动、覆盖升级保留数据、多窗口 Codex 重启、并发流式请求、工具调用、原生子任务、网络异常、连续运行和日志轮转。验证不依赖开发机上的 Python、Git 或仓库路径。

签名准备单列为公开发布前的里程碑：确认账号、证书、macOS 签名与公证流程、Windows 签名方案及构建凭据管理。测试包验收不代表已具备公开发布条件。

## 7. 验证策略与范围限制

复用现有协议测试；新增验证集中在配置事务、状态转换、实例互斥、控制协议和进程故障恢复，不为纯样式变更添加镜像式测试。安装、签名提示和 Codex 重启需要真实双平台验证。

首版不包含：Linux、Intel Mac、Windows ARM64、开机自启、自动更新、目录切换、CLI 图形化封装、请求历史、用量统计、自动强杀 Codex、保证任务恢复。

Clash Verge Rev 作为 Tauri 桌面工程参考；不以直接 fork 整个代理项目为实施路线。引用代码须按其许可证处理。

## 8. 阶段 0 的待验证事项

以下主要属于技术验证；桌面停服收尾仍需具体化。验证结果需回写本文，不能静默改变已确认的交互。

1. 两平台 Python 打包工具、资源布局和网关进程隔离方式；明确退出、崩溃和重试行为。
2. Codex 桌面运行状态识别的准确性及权限兼容；读取失败时显示未知。不再推进任务状态探测。
3. 可选桌面操作在退出受阻、配置失败及启动未确认时的反馈，以及配置已恢复但客户端可能仍依赖网关时的停服与退出收尾。
4. 配置冲突写入拦截、接入前基线的可信识别、旧数据兼容与互斥协议。
5. Codex 安装自动识别与正常重启的双平台差异；识别失败时提示手动操作。
6. 前端框架、桌面控制协议和配置管理接口拆分；以减少业务重写和控制权限为准。
7. 已具备双平台实机条件；阶段开始时安排构建工具链、设备测试方式和测试清单。签名账号、证书与公开发布流水线仍需另行落实，不影响先交付测试包。

## 9. 推进顺序与完成标准

后续恢复桌面开发时，按阶段 0 → 1 → 2 → 3 → 4 推进；当前网页工作按本文开头的网页验证进度迭代。先证明双平台打包、配置管理独立运行及 Codex 重启路径可行，再建立业务控制和恢复闭环，之后完成界面与双平台安装验收。

首版完成标准：普通用户在两种目标平台无需终端、Python 或 Git，能安装应用、配置并测试模型、通过单一主开关接入 Codex、正常重启 Codex、关闭接入恢复原生配置，并在故障时查看日志与导出脱敏诊断包。取消、冲突和失败均有明确状态与恢复入口。

当前已完成 Windows Python sidecar 隔离验证及最小 Tauri 骨架，尚未完成 Tauri 原生编译、macOS 打包实机和真实 Codex 重启验证，阶段 0 不标记完成。详细证据、已发现差距和复现步骤见[验证记录](stage0-validation.md)。日历工期在阶段 0 完整验证后评估；双平台测试包交付与签名后的公开发布分别验收。
